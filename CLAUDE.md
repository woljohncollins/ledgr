# CLAUDE.md: Ledgr

This is the operating manual for building Ledgr with Claude Code. Read it at the start of every session. It points to the deeper docs rather than repeating them, so keep it short and keep the pointers current.

**Ledgr** is a single-user personal life management system (replacing Notion) for Brandon Collins, Executive Pastor at Edgewood Community Church. It stores meetings, tasks, notes, and links as richly formatted items in Postgres, presented through a Next.js PWA with two surfaces (Work for daily use, Build for configuration; PRD §4.10), integrated with Microsoft 365, Todoist, and Claude (via MCP).

> **✅ Project status: v1.0 PRODUCTION (ADR-115, 2026-06-26).** Ledgr is in real daily use and holds **production data** (Brandon's Notion import landed 2026-06-26). The alpha exemptions are over: treat data as real. Schema changes get proper migrations (additive, then backfill; no destructive reseed of live owner data), back-compat matters, and production changes call for ordinary production care: be deliberate, prefer additive and reversible steps, and don't ship large, risky changes carelessly (there is **no fixed weekend/Saturday no-deploy window**, ADR-119). Soft-delete + revisions + the weekly backup + git revert are the safety net. (History: ADR-039 set the prior alpha/build-phase posture on 2026-06-13; ADR-115 records the flip and reverses it. Tyler's instance is separate and flips on his own timeline.)

## The non-negotiable rules

These come straight from the PRD's design principles. Breaking one is a design regression, not a style preference.

1. **DB is canonical; OneDrive export is one-way.** Never build bidirectional sync to files. The database is the source of truth.
2. **Everything is an item.** One `items` table, typed. Entities, tasks, meetings, notes, links, and user types are all rows in it. Don't add parallel tables for these.
3. **Deterministic by default, AI on purpose.** Routine plumbing (calendar matching, metadata extraction, formatting, sync) is plain code with no model in the loop. AI lives only in the deliberate, human-in-the-loop Claude/MCP layer, never in a cron job.
4. **Sunday-proof.** Nothing preached on Sunday may depend on Vercel, Neon, or church wifi. The OneDrive export and Pulpit Ready PDF are the fallback path. Don't weaken them.
5. **Boring stack, few dependencies.** Every new package is a future maintenance event. Justify additions; prefer what's already in the stack (e.g. Postgres `pg_trgm` over a new fuzzy-match lib).
6. **Bespoke-first, one catch-all.** Design each content type (notes, tasks, meetings, songs, papers, hiring, etc.) with built-in features and, where it earns it, its own canvas. One customizable catch-all type absorbs temporary or unanticipated uses; when a catch-all use proves itself, promote it to a permanent bespoke type (Claude Code does the conversion). This replaces the former "Notion-default" principle: Ledgr is no longer generic-first. Notion stays a reference for individual interactions and muscle memory where it fits, not the default shape of the system. (Pivot: ADR-037.)
7. **Multi-user-ready, not multi-user.** Every item carries `owner_id`; every query is owner-scoped. Build no invitations, permissions UI, or sharing-to-accounts in v1.
8. **Fast for the user, cheap on the back end.** Weigh both on every choice (see `runbook.md` perf rules): optimistic UI, stale-while-revalidate, lazy editor, virtualized lists; pooled connections, no `body` in list queries, incremental syncs, right-sized crons.
9. **Observable and debuggable.** Structured JSON logs with correlation ids, a toggleable debug mode, captured-and-surfaced cron/webhook errors (no silent failures), and docs kept current.

## Two modes, one rule (ADR-063)

**Work is for *using* the system. Build is for *building and maintaining* the system.** Every feature sorts onto one side of that line. **Work** is glanceable, mobile-friendly, a configurable bottom bar/rail of the user's daily destinations. **Build** is deliberate, desktop-first, a fixed left sidebar of system tools, grouped under three verbs: **DATA** (build the data model), **INTERFACE** (build how you see and reach it), **MAINTAIN** (understand and care for what exists).

**The separation is the default, not a wall.** Any navigable route — Work pages, saved views, type lists, *and* every Build/Maintain section — is a valid nav destination. A power user can pull a Build tool into their Work nav (a "Clean" button pointing at Data Hygiene, a "New Sermon" shortcut). We draw the use/build line for clarity of defaults; the user is free to punch through it deliberately (the destination picker's "Build tools" category makes it discoverable). Most users never will, and that's fine — the power is opt-in. The Build sidebar is a hardcoded system surface (`src/lib/build-nav.ts`, the single source of truth for the sidebar and the picker category); the Work nav is owner-configurable.

## Stack

- **App:** Next.js (single app) on Vercel
- **DB:** Postgres on Neon (free tier), always through the **connection pooler**, never a direct connection
- **Data layer:** Drizzle ORM + migrations (SQL-close, serverless-friendly; chosen over Prisma)
- **Editor & body format:** **Canonical body format is Markdown** (an extended dialect: CommonMark/GFM plus inline HTML `<mark>`/`<span>` for sermon colors/highlights, `<ins class="slide">` as the **slide mark** — "put this span on the screen," read by the presentation export, ADR-176 — a `<details>` **toggle block** for collapsible content (ADR-145), `++underline++` for underlined text (a StarterKit primitive the editor has always emitted; rendered everywhere as of ADR-178), and **CriticMarkup comments** — `{==anchored text==}{>>note<<}`, or `{>>note<<}` alone — as notes-to-self anchored to a span of the body, ADR-170). That list is the dialect's written contract, so **adding an element to it is a core change** (both-agree + ADR) and belongs in this sentence when it lands. It lists only what is actually built: nothing here is aspirational, so if you can't find the code that renders it, the list is wrong and should be fixed (ADR-190). **Pandoc footnotes are deliberately not in the dialect.** `[^id]` markers work only inside the Papers module, which hand-parses them in its own textarea and `.docx` exporter (ADR-048); everywhere else they render as literal text. Pandoc superscripts, citations, and attribute spans are not implemented at all. Adding any of them to the shared dialect would be a core change like any other. `items.body` stores `{format, text}` (jsonb), `format: "markdown"` by default; markdown-family formats like `chordpro` are allowed per type. Markdown is the **source of truth**; rich features layer on top of it per content type, and every other output (Word/`.docx` via the `docx` package, chord charts, slides, print/PDF) is **rendered from** the markdown, never stored as a second source. The editor is a **markdown-native WYSIWYG** surface (renders rich, not raw, with a likely source/preview toggle); the specific library is TBD (tiptap / Milkdown / Lexical with markdown serialization are candidates). A content type may declare its own canvas (chord editor, paper workspace); types without one get the default markdown canvas. The polished "Notion feel" (slash menu, block drag) is wanted but explicitly **not** a v1 requirement: revisit later, or adopt an existing lib. (Pivot from BlockNote-JSON-canonical: ADR-037.)
- **Auth:** Clerk (free tier), Microsoft sign-in primary. Machine-to-machine (MCP, cron, webhooks) uses scoped API tokens, separate from Clerk.
- **File storage:** Cloudflare R2 (object storage + CDN) behind a storage-provider interface; presigned URLs; per-user quota (~10GB). OneDrive gets backup copies via export.
- **Scheduler:** Vercel Hobby cron (daily only); sub-daily jobs triggered by a GitHub Actions workflow hitting authenticated endpoints.
- **Integrations:** Microsoft Graph (calendar, email-in, OneDrive export), Todoist (tasks/reminders/offline capture), Claude via a thin MCP server.
- **Cost target:** ~$0/month on free tiers (+ ~$12/yr domain).

## Provider-interface discipline

To keep a future local build (Phase 4) a packaging exercise rather than a rewrite, keep the three embedded cloud dependencies behind thin interfaces: **storage** (already), **auth** (Clerk reachable behind an interface so a local single-user mode can stand in), and the **scheduler** (GitHub Actions calls the same authenticated endpoints a local cron could). The DB is already portable via Drizzle (connection-string change).

## Working conventions

- **Owner-scope every query.** No query touches `items` without filtering `owner_id`.
- **List queries never select `body`.** Bodies load only when an item is opened.
- **Soft-delete only.** Deletes move to Trash (30-day purge); they don't hard-delete. Parent soft-delete cascades to children.
- **Snapshot bodies to `revisions` on save (debounced).** Cap ~50 per item.
- **Indexes are part of the feature.** When you add a queried field, add its index (see `schema.md`).
- **Incremental syncs only.** Delta/changed-since queries, never full re-pulls.
- **Be deliberate with production, no fixed deploy calendar (ADR-119, supersedes the no-Saturday-deploys rule).** Ledgr is in daily production use, so weigh changes that touch live data or production: prefer additive, reversible steps and lean on the safety net (soft-delete + revisions + the weekly backup + git revert); don't ship large, risky changes carelessly. There is **no blanket weekend/Saturday no-deploy window**: Brandon preaches only a few times a year, so a calendar ban was ceremony more than protection. If a specific deploy is genuinely sermon-sensitive on a given weekend, use judgment then; otherwise ship when ready. (Distinct from Principle 4 "Sunday-proof," the offline-fallback guarantee, which stands unchanged.)
- **The config file is never the end user's lever (Brandon, 2026-08-25; ADR-222).** Every setting a person is expected to change lives in the **GUI**. `supervisor/config.json`, env vars, and JSON blocks are for standing an install up and for testing, never for switching a feature on or off. If a surface's answer to "how do I turn this on?" is "edit this file and restart the service", the feature has not shipped: it has a builder attached. The pattern that makes this cheap is the one ADR-222 used for snapshots — schedule the job unconditionally and let the *endpoint* read a setting from the database, so the owner's control is a checkbox that takes effect on the next run with no restart. A leftover config knob is fine as a testing escape hatch; it just must not be the documented way anyone turns the thing on.
- **Standardized, generic language in the tool's UI.** Prefer plain, conventional product language over church-specific jargon for labels, buttons, and surfaces (e.g. "Save Offline", not "Pulpit Ready"; "Sync to Storage" over insider terms). Brandon is the only user, but the tool should read like a general product so its concepts stay portable. PRD section names can keep their original wording; this is about what's rendered on screen.
- **Batch work locally; do not open a PR per slice (Brandon, 2026-08-23).** Prefer several slices of local work — built, tested, and verified on the rig — before pushing to `main`, rather than a branch-and-PR reflex after every change. Still non-negotiable: never commit directly to `main`, and every merge still goes through a PR. What changed is the *cadence*: fewer, larger, coherent PRs instead of one per slice. Two things override this and go up promptly anyway: a **core change** (both-agree + ADR, per "Building together" below), and anything **Tyler needs to see** to avoid duplicating or colliding with work. Keep `next_steps.md` current locally as you go, so a batch that grows large is still legible when it lands.
- **Writing style for any prose Claude generates for Brandon:** no em dashes (use commas, colons, parentheticals, or rework); don't split a contrast into two choppy sentences; concise, direct, warm, active voice.
- **Scope the UI when you build something big (Brandon, 2026-06-21).** A significant feature must be understandable to the other builder without a walkthrough, even when tucked behind a "More" affordance. Give every bespoke control a clear label or tooltip; don't ship an unexplained one (the cautionary case: an event-canvas "tasks related to the people here" control with no label). If a feature is worth building, it's worth making legible.
- **Defer by hiding, not deleting (Brandon, 2026-06-21).** An over-built or not-ready feature gets hidden (scoped behind a default, a setting, or "More"), not ripped out or commented away, so it stays recoverable and the next builder still sees the intent. This is the feature-side analog of the soft-delete-only rule.
- **Every list surface includes multi-select (the standard, ADR-118; opt-in via a toggle, ADR-121).** Any list that renders rows of items gets row selection + the floating bulk-action bar, so the owner can act on many items at once. Wire it the reusable way, never per-page bulk logic: wrap the list region in `<SelectionProvider ids={…ordered in-view ids}>`, drop a `<SelectModeToggle />` just above the list (it's the right-aligned "Select"/"Done" entry point), drop a `<SelectCheckbox id={item.id} />` at the leading edge of each row, and render `<BulkActionBar {...bulkConfigForType(typeDef)} />` (or `{}` for a mixed-type surface, which then offers only Move + Delete). **Select mode is off by default** (ADR-121): `SelectCheckbox` renders nothing until the toggle turns it on, so an idle list reserves no leading space and shows no checkboxes on touch. The shared `ViewRenderer` already supports this via its `selectable` prop (its table layout uses `SelectHeaderCell`/`SelectBodyCell` so the checkbox column collapses when off). Bulk ops go through `/api/items/batch` (which reuses the same `updateItem`/`softDeleteItem` as the single-item routes). Board/calendar layouts, dashboard widgets, and Trash are the deliberate exceptions (defer-by-hiding; `selectable` off, no toggle). The reference wiring is the generic list (`src/app/list/[type]/page.tsx`).
- **Style refreshed surfaces from the token layer, not raw grays (the standard, ADR-141).** `globals.css` carries a two-tier token system. New or refreshed UI uses the **semantic classes** — `bg-surface-{0,1,2,3}`, `border-line`/`border-line-strong`, `text-ink`/`text-ink-muted`/`text-ink-subtle`/`text-ink-faint`, `rounded-card` (one 10px radius) — and the opt-in **type scale** (`ui-title`/`ui-section-label`/`ui-row`/`ui-meta`) on an 8px spacing grid, instead of hardcoding `bg-neutral-900`/`border-neutral-800`/etc. Existing neutral usages need not be rewritten: tier 1 routes `--color-neutral-*` through runtime `--n-*` vars, so they already flip with a future `.light` class (mechanism proven at `/dev/theme`, dev-only). The `neutral-N → semantic` mapping guide is the comment block atop `globals.css`. Cap numeric badges with `badgeCount()` from `src/lib/format-count.ts`. Don't add a competing color vocabulary; extend this one.
- **Row actions live in the shared RowMenu + a global undo toast, not per-row buttons (the standard, ADR-142).** A list row gets its actions from `RowMenu` (`src/components/lists/RowMenu.tsx`) — opened by right-click (desktop) and long-press (touch): Complete/Focus/Schedule for task-like rows (`canComplete`), Move-to-Trash for every row. Wire it the reusable way: wrap a plain row in `<RowMenu id={…} className={…} canComplete done today label>`, or spread `useRowMenu(opts)`'s `{handlers, menu}` onto a row that renders its own `<li>` (e.g. `SubtaskExpandableRow`'s `menuOptions`). Don't add an always-visible per-row Trash/action button (the retired `RowAction` pattern). Fire user feedback for destructive/one-way actions with `showToast(text, undo?)` from `src/components/ui/ActionToast.tsx` (mounted once in the root layout so it survives `router.refresh()`); soft-delete + the undo toast are the safety net. Swipe (`SwipeRow`, ADR-142/S5) and the mobile launcher (S6) build on the same posture: non-destructive by default, Trash stays in the menu.
- **Tooltips are CSS hover tooltips with a `cursor-help` target (the standard, 2026-06-15).** When a label/control needs an explanatory tooltip, wrap it in a `group relative` element with `cursor-help`, give the trigger a dotted underline (`underline decoration-dotted decoration-neutral-600 underline-offset-2`) as the "hover me" affordance, and reveal a `role="tooltip"` panel on `group-hover` (`pointer-events-none absolute z-20 … opacity-0 transition-opacity group-hover:opacity-100`, dark `bg-neutral-900` + `border-neutral-700` + shadow, `normal-case` body text). No JS, no tooltip dependency (Principle 5); works in server components. The pattern on the Build → Types "Quick capture" header (`src/app/build/types/page.tsx`, ADR-059) is the reference; prefer this over the native `title` attribute for anything explanatory. Right-align the panel near a screen/column edge so it doesn't overflow.

## Building together (Brandon + Tyler)

Ledgr is now built by two people sharing one codebase and schema, each deploying their own single-tenant instance (separate Vercel + Neon; `owner_id`-everywhere makes this clean). The risk in the foundation phase is not scheduling, it's two people making different decisions about the same core. Guardrails:

- **Core is frozen behind agreement.** A change to anything in the **core list** below needs both people to agree and an ADR in `decisions.md` before it merges. Everything else, either person moves fast on, solo.
  - **Core (both-agree + ADR):** the data model / `schema.md` (`items`, `types`, `relations`, `revisions`, properties, owner-scoping); the **canonical body format** and its `{format, text}` contract; the **type + canvas model** (bespoke-per-type, the single catch-all, the promotion path, how a type declares a canvas); the **module system boundary** (how a module registers its type/canvas/exporters/integration, and the per-user enable model); the **provider interfaces** (storage, auth, scheduler, calendar, mail, push, tasks); the cross-cutting invariants (owner-scope every query, no `body` in list queries, soft-delete + revisions, the FTS approach, incremental syncs); the **machine/MCP API contract** (see the carve-out below); and the nine principles above.
  - **Carve-out: purely additive MCP/API surface is NOT core (ADR-183).** Adding a tool, adding an optional argument to an existing tool, or adding a field to a response is a solo, move-fast change. A more capable API can't hurt how the app is used, and gating it behind both-agree only slowed the person doing the work. What stays core is **changing or removing** what already exists: renaming or deleting a tool, changing an argument's meaning or a response's shape, tightening validation on an existing call, or changing how a tool authenticates. Rule of thumb: if an existing caller keeps working byte-for-byte, ship it solo and note it in `COLLAB.md`.
  - **Not core (move fast, solo):** individual module internals (papers, songs, discipleship, sermons, hiring — their canvases, exporters, stage models); UI/UX polish; view definitions and dashboard widgets; per-instance adapter choices (Microsoft vs Google vs iCloud) and per-instance integrations (Savor, Atlas, PCO).
- **`COLLAB.md` is the heads-up board.** Two sections only (Brandon, Tyler), each holding *current* availability and plan ("away until Tuesday," "this week: papers module"). Overwrite in place, no archive. Pair it with a quick Discord/Telegram ping. Decisions go in `decisions.md`; plans go here.
- **Modules are standalone on a shared frame.** Build each module so it registers onto core rather than reaching into it. Keep boundaries clean now so per-user enable/disable is a later config flip (module-ready, not a marketplace — the analog of "multi-user-ready, not multi-user").

## When you finish a slice

**If the slice changed what the owner can do, update the user guide in the same PR (ADR-189).** The guide is one markdown constant in `src/lib/mcp/user-guide.ts`, served three ways: the MCP resource `ledgr://guide/using-ledgr`, the in-app page at `/build/guide`, and the links that reach it. It exists because a feature nobody knows about is indistinguishable from a feature that was never built — which is how Tyler kept asking for things he already had. The test is not "did I touch code," it's **"can the owner now do something they couldn't, or reach something somewhere new?"** A new feature, a new route, a renamed control, a retired affordance: all of those move the guide. A refactor, a bug fix, or a perf change does not. Nothing generates the guide from code, on purpose — a generated index reads worse than a maintained one — so this reminder and the `/ship` gate are the whole mechanism. Keep it instance-agnostic (it serves both deploys) and describe only what exists; `scripts/verify-user-guide.mts` fails if the guide cites a `/build/…` route that isn't real.
