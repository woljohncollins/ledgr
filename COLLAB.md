# COLLAB.md — heads-up board (Brandon + Tyler)

The two-person coordination surface for Ledgr. **Two sections, current state only, overwrite in place — no archive.** Each person keeps their block to "where I am and what I'm doing next" so the other isn't guessing. Pair it with a quick Discord/Telegram ping for anything time-sensitive.

**Where things go:**
- **Plans / availability / "what I'm touching this week"** → here.
- **Decisions** (anything architectural) → `decisions.md` as an ADR.
- **The core-change contract** (what needs both-agree before it merges, and what doesn't) → CLAUDE.md, "Building together." Read it before touching anything foundational.

Rule of thumb: a change to **core** (data model, the canonical body format, the type/canvas model, the module boundary, the provider interfaces, the cross-cutting invariants, the MCP/API contract, the nine principles) needs **both-agree + an ADR**. Everything else, move fast solo.

- **⚪ FYI, shipped solo 2026-08-27 — a local peer now comes back from an unclean reboot on its own, and has an icon (ADR-229).** Local-supervisor lifecycle only: no schema, no wire format, no seam, nothing your cloud deploy renders or runs. Skip the detail if you never run a peer, but **two findings generalize past this repo and cost me an outage each.** (1) **A process id is not an identity, and Windows reissues low pids fastest right after a boot — exactly when your stale files are freshest.** Brandon's peer did not come back from a restart because `pg/postmaster.pid` named a pid that now belonged to a stranger, so Postgres refused to start; and `supervisor.lock` named another, so `local:status` cheerfully reported "supervisor running (pid 4080)" for the entire outage while nothing served, and every attempt to start one was refused as a duplicate. Anywhere you have a pid file, `process.kill(pid, 0)` is not the question — "is that process the thing I think it is" is, and the command line answers it. The `ponytail:` comment sitting on that function had named this precise window eleven days earlier and judged it too narrow to close. (2) **`process.exit()` right after a `fetch` trips a libuv assertion on Windows** (`!(handle->flags & UV_HANDLE_CLOSING)`, `src\win\async.c`) and kills the process with **status 127 after the work succeeded**. Invisible from a terminal; not invisible to anything reading exit codes, which in our case would have recorded every successful boot as a failed scheduled task. `process.exitCode = n` and letting Node wind down is both correct and faster (~160ms vs ~430ms). Worth grepping your own scripts for. (3) **If you ever print a Windows command for a human to paste, the SHELL is part of the command.** Our "run this in an Administrator PowerShell" line carried cmd.exe backslash-quote escaping and failed on paste — fine, loud, fixable. The part worth knowing is that the two obvious repairs (single-quote the argument, or put it in a variable) both report **SUCCESS** and register a task whose command has lost every quote, because PowerShell re-quotes native arguments on the way to the exe. Verified by reading back what Windows actually stored for all three forms. It works until a path has a space in it. `--%` is the fix for a pasted line; passing an argv from Node is the fix for anything programmatic. **The rest, briefly:** Windows now starts `ledgr-ctl boot` rather than the supervisor, because a Task Scheduler action has no stdout and a supervisor launched directly wrote its startup into nowhere — which is why the original failure left the single word "undefined" as its reason. `boot` is idempotent, attaches the log files, and clears provably-stale locks, so recovery is unattended (measured: 4.4s from the reproduced outage). And there is a **notification-area icon** now (`npm run local:tray`, PowerShell + WinForms, no new dependency): green/amber/red with right-click Open, Check status, Start, Restart, Stop.
